# NOTES — TASK-083 execution (star pick ray origin in parsecs)

Judgment calls logged as they happened (CLAUDE.md "Judgment calls").

## 1. Exactly one of three `position.local` reads was scaled — the frozen surface held

`StarScene.tsx`'s picking effect reads `controller.state.position.local` in **three** places:
the local-group galaxy pick (`:235`, universe-only, TASK-086, own Mpc convention), the star
pick (`:260`, the target), and `projectToScreen` (`:278`, self-consistent — subtracts two
context-unit quantities, no parsec term). Only the star-pick read is the bug. Scaled that one
by `pcScales(controller.contextId).unitsToPc`; left the other two untouched. Confirmed
`projectToScreen` must NOT be scaled by the live measurement itself: it is what places the star
on screen correctly in system context (the test relies on it), so scaling it would break the
test's own oracle. The spec's §Frozen surface predicted this; it verified true.

## 2. `?debug=m4a` reused as the system-context vehicle (same as TASK-084)

The new spec needs settled `contextId === 'system'` with the star field live. `M4aApp` +
`M3DescentProbe` already provide exactly that (galaxy → system descent to Sol), and
`system-context-scale.spec.ts` already models the wait pattern. No new probe app.

## 3. Star position comes from the manifest (m1 pattern) — the spec's flagged "STOP" was a false alarm

The spec's Deliverable 2 flagged a possible STOP: "if no `__cosmos` read exposes a star's
context-frame position, the test needs a new hook." It doesn't need one. `m1.spec.ts` gets star
positions by fetching `/packs/manifest.json` + the bin (`positionsPc`), and passes the raw
parsec position to `projectToScreen` — which works there only because galaxy units == parsecs.
In system context the same fetch works with one added step: convert parsecs → system units by
`contextUnitMeters.galaxy / contextUnitMeters.system` (the app's own table, not a hardcoded
ratio). No new read hook. Removed the false STOP from the spec during the readiness measurement.

## 4. Target selection: nearest on-screen star, with a pixel-isolation filter

The live measurement (research doc) showed the fix flips pick from 0/40 → 36/40 match at
on-screen stars. The 4 residual "misses" were **exact co-located star pairs** projecting to one
pixel (e.g. `hyg:118079`/`118080` → (241,439)); the angular pick legitimately resolves either.
To make "pick must return the projected star" an unambiguous assertion, the test picks the
nearest on-screen star with **no other on-screen star within `MIN_NEIGHBOUR_SEP_PX` (6px)** —
excluding the tie blobs. No hard-coded pixel or star id: the target is computed at runtime from
whatever pack is served (CLAUDE.md rule 2). Ran at the config's 1280×720, different from the
882×910 of the manual measurement — the runtime-computed target absorbed the difference, which
is the point of not hardcoding geometry.

## 5. Power proof: fail-on-main → pass-on-fix, deterministic same target

`git stash push apps/web/src/scene/StarScene.tsx` (revert only the fix, keep the new spec),
rebuilt web, reran the spec:

- **main (no fix):** target `hyg:16496` (101,513, 3.22 pc) → `pickAt` returns `hyg:16729`
  (a different star). **FAIL** — exactly the on-`main` symptom.
- **fix:** same deterministic target `hyg:16496` → `pickAt` returns `hyg:16496`. **PASS**.

Same target pixel both runs, so the flip is attributable to the fix alone. Restored via
`git stash pop`.

## 6. Live-verification gotcha (tooling, not code): HMR did not reach the pick closure

While verifying in the dev preview, the first post-edit probe still returned the buggy id — HMR
updated the module but the live `pickAt` closure (registered once in the effect) was not
re-created, so it kept the old code. A hard reload (re-run of the descent) picked up the fix and
flipped 0/40 → 36/40. Noted so a future verifier doesn't trust an HMR-only reload for closures
captured in an effect.
