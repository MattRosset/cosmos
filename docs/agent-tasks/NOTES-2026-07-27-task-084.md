# NOTES — TASK-084 execution (SystemScene context-scaled bodies)

Judgment calls logged as they happened (CLAUDE.md "Judgment calls").

## 1. `controllerRef` was already a prop, just voided — used it instead of adding a new one

The spec's D2 needs the active `ContextId` inside `SystemScene`'s frame loop. `SystemScene`
already received `controllerRef` (a `RefObject<FlightController | null>`) but discarded it
(`void controllerRef; // picking is handled by StarScene`). Read `controllerRef.current?.contextId
?? origin.context` — the exact fallback expression `StarScene.tsx:169` and `GalaxyScene.tsx:480`
already use for the same question (TASK-081's established pattern) — rather than plumbing a new
prop or context.

## 2. Acceptance gate 3 (the measurement) needed new read-hook surface — added the minimum

The gate asks for a live measurement via `projectToScreen` (center + limb), reading r/d "from
the app". Existing hooks (`systemFeed`, `test-hook.ts`) had radii and absolute AU positions but
not the camera-relative render offset per body, nor a way to read the actual live
`mesh.object.scale.x` SystemScene wrote to the rendered THREE object. Added:

- `systemFeed.renderOffsetsContextUnits` — mirrors the same `renderScratch` value already
  passed to `mesh.setRenderOffset` each frame (zero new computation, just an extra store).
- `testHook.systemBody(bodyId)` — reads `radiusAu`/`renderOffsetContextUnits` from `systemFeed`
  and `meshScaleX` by walking `systemPickGroup.current.children` for the matching
  `userData.bodyId` and reading `.scale.x` **directly off the live scene graph** — not a mirror
  of the frame-loop's local `sizeScale` variable, so it actually proves D2's write reached the
  rendered object (a mirror of the same variable would trivially match by construction and prove
  nothing about wiring).
- `testHook.contextUnitMeters` — a passthrough of the app's own `CONTEXT_UNIT_METERS` table, so
  the e2e test doesn't hardcode a duplicate of the physical constants (rule 1).

## 3. Picked `?debug=m4a`, not `?debug=m3`, as the galaxy-context vehicle

The spec's Out-of-scope section already documents that `M4aApp` (unlike `M3App`) keeps the
system mounted in every context (`mountedSystemId ?? M3_SOL_SYSTEM_ID`), specifically so
`flythrough4.spec.ts`'s baseline isn't disturbed. That's exactly the reachable-from-galaxy path
TASK-084 fixes, and it comes with a ready-made scripted descent (`M3DescentProbe`) that spends
real frame-time in `galaxy` context flying toward Sol before switching to `system` — no new
probe app needed.

## 4. The measurement has to run INSIDE the page, at the moment contextId is 'galaxy'

First draft computed the projected diameter in Node, after `await waitDescentDone(page)`. That's
wrong: by the time `__m3Result` resolves the descent has already reached `system` context, so
calling `__cosmos.projectToScreen` then evaluates against the CURRENT (system-anchored) camera
position, not the galaxy-context vantage the sample was taken from — silently wrong numbers, not
an error. Moved the entire measurement (perp-axis construction, both `projectToScreen` calls)
into the `addInitScript` rAF sampler, so it runs synchronously with the live camera state, and
only the finished numeric result crosses back to Node.

## 5. `contextId`/`goToActive` are mirrored on a 250ms timer, not per-frame — first run flaked

First run against the real fix passed the `galaxy` sample but never captured a `system` sample
(`result.system === null`) even though the descent visibly finished. Root cause:
`installTimeGlue` (`apps/web/src/glue/time.ts:62-70`) mirrors `contextId`/`goToActive` onto
`window.__cosmos` from a `setInterval(..., 250)`, not from a frame callback — the test's rAF
sampler was reading a stale mirror that hadn't caught up to the just-finished descent yet within
the test's remaining lifetime. Fixed by adding an explicit
`page.waitForFunction(() => contextId==='system' && goToActive===false)` after `waitDescentDone`,
giving the mirror its 250ms to catch up before reading the sampler's stored result.

## 6. Sanity-checked the gate is not vacuous — mutation test, not just argument

Temporarily commented out `e.mesh.object.scale.setScalar(sizeScale)` (simulating the pre-fix
state: THREE's default `scale=(1,1,1)`) and reran the new spec: it failed with
`meshScaleX=1` vs `expectedScale=4.848e-6`, ratio **206,265.3×** off — matching the spec's own
stated bug magnitude (206,266×) almost exactly. Restored the fix and reran: passes, with
`measuredDiameterPx === expectedDiameterPx` bit-for-bit (both `5.002220859751105e-12`) and
`system`-context `meshScaleX` bit-identical `1`.
