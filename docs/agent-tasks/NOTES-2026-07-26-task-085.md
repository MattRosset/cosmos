## Judgment calls

1. **Branch point.** Work landed on `fix/task-085-overlay-context-scale` cut from
   `fix/task-080-universe-ascent`, not from `main`. Not stated by the spec, but forced:
   Deliverable 7's spec clicks the `◂ Universe` breadcrumb, which only exists on the
   TASK-080 branch. Merge order stays 085 → 080.

2. **`FrameStats` is an exported named interface.** The spec wrote `readFrameStats` with an
   inline return type. `apps/web` typechecks with `declaration`-style strictness and the
   inline object read badly at the call site, so the shape is a named exported interface and
   the method returns `Promise<FrameStats | null>`. Same fields, same units.

3. **The e2e spec types the hook through a local `ScaleHook` cast.** The global `Window`
   augmentation for `__cosmos` lives in `m1.spec.ts` with the M2/M3 shape and has no
   `overlays` / `procgenOpacity` / `readFrameStats`. Widening a shared global from a new
   spec would touch every other spec's type surface; `m4a.spec.ts` already set the
   local-interface-plus-cast precedent, so this spec follows it.

4. **`page.keyboard.press('Escape')` closes the View drawer.** The spec said "close the
   drawer (press Escape)" without naming the API; this is the Playwright form.

5. **The tier assertion is a separate `expect` after the `waitForFunction`.** The wait alone
   would time out rather than report the observed tier; F7 asked for the value in the
   message, so the tier is re-read and asserted explicitly.

## Findings to report (no code change here)

   task's doing.** Gate 4 says a moved galaxy baseline means STOP. Measured before
   concluding anything: with TASK-085 stashed and the app rebuilt, `m1-betelgeuse` fails
   with **67,394** differing pixels (ratio 0.08); with TASK-085 applied it fails with
   **67,415**; two further runs of the *unchanged* tree also produced **67,415**. So the
   ±21 px is run-to-run noise on this machine and the drift is pre-existing (it predates

   it belongs to whoever owns that baseline). `m1-initial` passes in every run. Screenshots
   are reference-machine-only and non-gating on CI, so this does not block, but it must be
   stated in the PR rather than silently re-recorded.

7. **System context: NOTHING appears at the Saturn vantage, contrary to the spec's
   arithmetic prediction of a ~19° Orion nebula.** Measured with a temporary probe (deleted)
   that parks at the *same* vantage on both trees — the first attempt compared two different
   camera positions and was discarded as not-a-comparison:

   | tree | camera (system units) | meanLuma | litFrac | hotFrac |
   | --- | --- | --- | --- | --- |
   | pre-fix | `[-6.8216207, 2.1247855, -5.7485988]` | 6.79690 | 0.0436491 | 0.0036480 |
   | post-fix | `[-6.8216207, 2.1247855, -5.7485988]` | 6.79686 | 0.0436480 | 0.0036480 |

   A one-pixel difference in `litFrac`; the frame is unchanged. `m2.spec.ts` agrees — the
   `m2-saturn` baseline passes untouched with the fix applied.

   The mechanism is almost certainly the **camera far plane**: `StarScene.tsx:29-30` sets
   `near/far = 1e-6 / 1e6` in *render units*, and in `system` context those units are AU, so
   `neb:orion` at 415 pc ≈ **8.6e7 AU** sits ~86× beyond the far plane and is clipped
   whether or not it is correctly sized. That is read from source, not ablated — treat it as
   the leading hypothesis, not a measurement. It is also consistent with TASK-081's
   out-of-scope note that clip planes are a separate, unaddressed problem. **Follow-up
   material, not this task**: the overlays are now physically correct in `system` and simply
   fall outside the frustum.
