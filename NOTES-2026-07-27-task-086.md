## JC-1 — orient-helper gap (flagged by the task prompt itself)

The spec/prompt correctly identified that there is no generic "look at an arbitrary point
without flying there" production hook, and `FlightController.goTo` is gated
(`if (d0M <= opts.arrivalDistanceM) return;`), so a zero-distance target is a no-op.

Resolution: added `window.__cosmosDev.orientTo(local)` (universe-context only), which nudges
the camera by `EPS_UNITS = 1e-6` universe units (≈ 3.0857e16 m ≈ 1 pc) toward the target while
slewing orientation to face it exactly via `lookAtTarget`. `arrivalDistanceM =
EPS_UNITS * CONTEXT_UNIT_METERS.universe * 0.5` so the flight is reachable (`d0M` at exactly
`EPS_UNITS` universe-units is `2x` that arrival distance). `durationMs = 600` (short but not so
short the orientation slew — `CINEMATIC_LOOK_TC_MS`-style exponential blend inside
`updateGoToFrame` — visibly settles within one poll tick).

Why 1e-6 universe units is safe: the ONLY thing that can flip `contextId` away from `universe`
while ascended is `shouldEnterGalaxy`, which measures distance to the **galaxy anchor**
(`proc:milkyway`, pinned at `[0,0,0]`) — never to the orient target. The settled ascent vantage
is 0.18 Mpc from the origin (`viewUniverse`'s `UNIVERSE_VIEW_ARRIVAL_M` comment), 3.6x the
0.05 Mpc `enterGalaxyAtM` gate. Moving the camera by 1e-6 Mpc (≈ 1 pc) cannot close a 0.13 Mpc
gap, regardless of which of the 11 galaxies is the orient target — so no direction-dependent
choice was needed (unlike the prompt's fallback suggestion to "pick a galaxy index whose
direction doesn't pass near the origin"). Verified empirically in the e2e smoke run: contextId
stayed `universe` throughout `orientTo` calls in both G3 and G4.

## JC-2 — PICK_MAX_ANGLE_RAD: duplicate, not re-export

`StarScene.tsx`'s `PICK_MAX_ANGLE_RAD = 0.02` is a local (non-exported) constant in
`apps/web`. `pickNearestGalaxy` lives in `packages/nav` (D4: "pure, node-testable"), a lower
layer that cannot import from `apps/web` (dependency direction), and `@cosmos/nav`'s public
index does not currently export the constant. Re-exporting it from `apps/web` would mean
`packages/nav` importing from the app that depends on it — backwards. So the value is
duplicated in `packages/nav/src/local-group.ts` as `GALAXY_PICK_MAX_ANGLE_RAD = 0.02`, with a
comment tying it explicitly to `StarScene.tsx:20`'s `PICK_MAX_ANGLE_RAD` so a future change to
one is at least discoverable via grep for the literal `0.02` + the comment. This satisfies D6
("do not silently duplicate a magic number without a comment tying it to StarScene.tsx's
constant").

## JC-7 — e2e settle wait: fixed timeout, not a `goToActive` poll

First draft of both G3 and G4 specs polled `window.__cosmos.goToActive === false` to detect
`orientTo`'s flight settling before reading `projectToScreen`/`pickAt`. This flaked
intermittently (measured directly: `pickAt` returned `null` on one repeat of the G4 spec
despite `projectToScreen` having resolved a pixel moments earlier). Root cause: `goToActive`
on `window.__cosmos` is mirrored only on a ≤4 Hz timer (`apps/web/src/glue/time.ts`'s
`setInterval(..., 250)`), not live — so the FIRST `waitForFunction` check can observe a stale
`false` left over from the vantage-arrival flight, before the mirror ever ticks to reflect that
`orientTo`'s own (much shorter, 600ms) flight has started. The poll then resolves immediately,
and the test reads `projectToScreen`/computes the click pixel while the camera is still
mid-slew — by the time the real click dispatches, the galaxy has moved off that pixel.

Fix: replaced the `goToActive` poll with a fixed `ORIENT_SETTLE_MS = 1_000` wait (`page.
waitForTimeout`), matching the existing precedent in this repo for post-flight settling
(`ctxswitch.spec.ts` / `m3.spec.ts`'s `KEYFRAME_SETTLE_MS = 1_000`). `orientTo`'s own
`durationMs` is 600ms, so 1000ms clears it with margin. Verified stable over `--repeat-each=3`
runs of both specs after the fix (previously flaked ~1-in-3 on the select spec, 0 failures in
6 repeats after).
